# Release notes (draft) — `@osva-ai/connector-postgres@0.1.0`

**Status:** Draft for first public npm release. **Not published** as of P0.6 preparation.

## Summary

First public npm release of the OSVA PostgreSQL connector: MCP stdio server with **five read-only tools**, catalog discovery, bounded parameterized `SELECT`, database-enforced read-only transactions, and packaged-install acceptance against PostgreSQL 16.

## Included MCP tools (all read-only)

| Tool                       | Description                                                   |
| -------------------------- | ------------------------------------------------------------- |
| `postgres.connection.test` | Health check (`SELECT version()`)                             |
| `postgres.schema.list`     | Accessible non-system schemas (fixed catalog SQL)             |
| `postgres.table.list`      | Tables/views visible to the connected role                    |
| `postgres.column.list`     | Columns with column-level `SELECT` where applicable           |
| `postgres.query.read`      | Single parameterized read query (`SELECT` / `WITH` / `UNION`) |

**No SQL write tools** (no `INSERT`, `UPDATE`, `DELETE`, or DDL tools).

## Platform and dependencies

- **Node.js:** `>=24`
- **Transport:** MCP stdio (`osva-connector-postgres` CLI)
- **Connector SDK:** `@osva-ai/connector-sdk@1.1.0-rc.2` (release candidate)
- **PostgreSQL tested:** **16** (`postgres:16-alpine` in CI and packaged acceptance). Other major versions are not claimed.

## Security and authorization (tested vs deployment)

**Tested in CI / acceptance**

- Least-privilege integration role (`osva_reader`) with schema/table/column grants and RLS fixture behavior
- Discovery honors optional `OSVA_CONNECTOR_POSTGRES_ALLOWED_SCHEMAS` (defense in depth; does not widen DB privileges)
- `postgres.query.read` uses explicit **`BEGIN READ ONLY`** transactions with transaction-local timeouts
- SQL admission rejects obvious mutations and multi-statement input (parser-based; **not** a complete hostile-SQL sandbox)
- Sanitized MCP errors (no credentials, connection strings, or raw driver stacks in tool results)
- Routine logging design avoids SQL, parameters, and URLs (operator log aggregation still treated as sensitive)

**Deployment assumptions (operator responsibility)**

- Production authorization remains **PostgreSQL grants and RLS**, not MCP tool discovery
- TLS mode via `OSVA_CONNECTOR_POSTGRES_SSL_MODE` (`verify` recommended for remote hosts)
- MCP hosts must protect `OSVA_CONNECTOR_POSTGRES_URL` and treat query **result rows as sensitive provider content**
- Agents require OSVA ToolPolicy / human approval as your platform defines — MCP `tools/list` is not approval

## Query execution and limits (tested)

- Parameterized queries only (`$1`, `$2`, …); connector does not concatenate parameter values into SQL
- **Row cap:** `maxRows` default 100, max 500; **`truncated`** metadata when capped
- **Structured JSON budget:** 256 KiB on `structuredContent` per tool response
- **Cursor-based fetch** for `postgres.query.read` (bounded batches; not unbounded `pool.query` dumps)
- **Timeouts:** connection acquisition, PostgreSQL `statement_timeout`, and total wall-clock deadline for `postgres.query.read`
- **Cancellation:** MCP `AbortSignal` honored between batches; in-flight PostgreSQL work may continue until `statement_timeout` or pool cleanup

## Known limitations

- No cross-call snapshot consistency for discovery or ad-hoc SELECT
- Schema allowlist applies to **discovery tools only**, not arbitrary SQL in `postgres.query.read`
- SQL admission + `READ ONLY` do not sandbox untrusted arbitrary SQL (functions, cost, side channels)
- No pagination tokens for query results
- Connector SDK dependency is an **RC** pin for Connector Profile V1 compatibility testing
- Mid-flight cancel is not guaranteed to stop PostgreSQL instantly

- Local / CI: tarball install outside monorepo, npm bin shim, all five tools via packaged stdio against PostgreSQL 16
